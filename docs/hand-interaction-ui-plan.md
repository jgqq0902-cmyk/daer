# 大贰牌桌与手牌交互调整方案

## 目标

参考用户提供的实战牌桌截图，将 Godot 版从“信息面板中的牌局”调整为“以桌面和当前动作优先的对局界面”。本方案覆盖牌桌布局、动作响应、牌面组织、手牌拖动与暗色锁定搭子；不改变大贰规则、AI 决策、动作协议或结算。

设计方向为深色绒面牌桌与宣纸牌面的对比：桌面信息只保留本回合需要的内容，玩家手牌和待响应牌是第一视觉层级，设置、回放、AI 解释退居次要入口。

## 当前问题

现有 Godot 牌桌已具备三方座位、中心弃牌、手牌组合列和底部行动台，但和截图目标仍有四个差距：

1. 两名 AI 都集中在顶部，缺少围绕中心桌面的座位关系；当前行动和目标牌不够醒目。
2. 响应动作主要落在底部横向按钮栏，玩家要在“手牌、中心弃牌、操作栏”之间来回确认，吃/碰/招/胡的判断路径不够就地。
3. 当前 `_hand_groups()` 在 Godot 本地把顺、二七十、对子等牌效结构分组。它适合理牌，但不能证明这些牌在规则上不可拆；若用它直接标成暗色不可拖动，会制造错误规则事实。
4. 手牌目前只能点击选中，不能按自己的习惯把散牌、可拆组合重新排列。

## 总体布局

本项目为三人局，采用截图的围桌信息层级，但不复制四人局座位。

```text
┌──────────────── 顶部状态条 ────────────────┐
│ 局号 / 回合 / 牌山 / 服务状态        设置 回放 │
├────────────────── 深色牌桌 ─────────────────┤
│  玩家1（左上）               玩家2（右上）  │
│  名称、剩余张数、背牌、已亮组合              │
│                                               │
│              本轮目标牌 / 摸牌牌              │
│          出牌来源、胡息/回合、最近弃牌         │
│           [胡] [招] [碰] [吃] [过]            │
│                                               │
│     暗色锁定搭子区       可拖动普通手牌轨道     │
│            玩家（底部中央）                    │
└─────────────────────────────────────────────┘
```

### 固定区域

| 区域 | 1280x720 建议高度 | 内容与交互 |
| --- | ---: | --- |
| 顶部状态条 | 42-48 px | 最少显示阶段、回合、牌山、离线/在线；AI trace 与设置不抢占中心空间。 |
| 对手区 | 120-140 px | 玩家1 左上、玩家2 右上；只显示名字、牌数、背牌、公开 meld 与当前行动高亮。 |
| 中心行动区 | 220-250 px | 当前弃牌/翻牌最大化显示，来源和响应按钮紧邻目标牌。 |
| 玩家手牌区 | 230-260 px | 左侧暗色锁定搭子，右侧或中央为可拖动普通手牌；手牌轨道不再挤占动作区域。 |
| 辅助操作条 | 40-48 px | AI 建议、理牌、回放、返回等低频操作；不放主响应按钮。 |

窗口缩小时保持手牌区和中心行动区的最小高度；优先缩小对手背牌、历史弃牌和辅助文字，不能压住玩家牌或动作按钮。

### 座位与中心

- 玩家保持底部中央，手牌朝上，操作方向自然指向中心。
- 玩家1与玩家2分列左上、右上；轮到某席时该席仅用金色描边和小型“行动中”标记，不使用整块闪烁背景。
- 中心只突出一张“待处理牌”：响应阶段取 `discardPile.lastDiscard`；摸牌阶段取 core 明确声明的摸牌/待响应牌。普通弃牌历史缩成不超过 6 张的小列，不能与当前牌竞争。
- 对局状态文本贴近中心牌，例如“玩家2打出 7，等待你的响应”，不在底栏重复同一段长文本。

## 动作响应方案

### 响应阶段

当 `phase=response_collecting` 且当前玩家为玩家 0 时，中心行动区进入响应态：

- 在目标牌下显示来源、动作优先级和可响应数量。
- 根据 core 返回的 `availableActions` 显示实际可用的 `hu`、`zhao`、`peng`、`chi`、`pass`，顺序固定为 `hu → zhao → peng → chi → pass`。
- `hu` 使用最高对比度的绿色主按钮，`pass` 使用低饱和红棕色取消按钮，其他组合动作用金色边框。颜色只表达交互优先级，不参与规则判断。
- `chi` / `hu` 有多个 option 时，点击后在中心牌旁展开“方案带”，每个方案直接预览 `selectedCards` 和结果牌组；用户选定 `chiOptionId` / `huOptionId` 后才提交。
- 不存在的动作绝不显示；core 只给 `pass` 时中心只显示“过”，不以 UI 推测可吃、可碰或可胡。

### 出牌与摸牌阶段

- 出牌阶段保留“点击选中 + Enter 出牌”，主出牌按钮放在玩家手牌轨道右端；选中的牌上移 12 px，轨道不重排。
- 摸牌阶段把 `draw` 放在中心牌山附近，点击区域与牌山关联；若规则为自动翻牌/自动推进，则显示只读过程态，不提供伪按钮。
- AI 回合不显示“推进 AI”作为常规主操作。常规自动推进保持现状；“单步推进/原版策略”改入调试或设置入口，避免日常牌桌看起来像开发工具。

## 手牌组织与拖动

### 两类手牌

| 类型 | 权威来源 | 视觉 | 可选中/出牌 | 可拖动 |
| --- | --- | --- | --- | --- |
| 规则锁定暗搭子 | Bridge 依据 core 的锁定牌检测生成 `lockedHandMelds` | 灰黑牌面、低亮度边框、搭子标签、锁标记 | 否 | 否 |
| 普通手牌与视觉组合 | `players[0].cards` 减去锁定 ID；Godot 本地布局 | 正常宣纸牌面、红黑毛笔字 | 仅当存在于 `availableActions.discard` | 是 |
| 已亮组合 | `players[0].melds` 且 `isConcealed=false` / `position=table` | 小牌列，显示在手牌轨道外侧 | 否 | 否 |

暗色搭子只能表示核心规则已经锁定的坎、手中四张同牌等，绝不能把普通顺子、二七十、对子、大小搭或 AI 建议的潜力牌渲染成不可拆暗牌。它们可以被自动理到一起，但必须保持可拖动、可拆开和可出牌（以 `availableActions` 为准）。

### 权威锁定搭子接口

现有 core 已用 `MeldDetector.detectTriples()` / `detectQuadruples()` 和 `TurnManager` 拒绝锁定牌的弃牌动作，但常规 `PlayerHand.melds` 只保存已亮组合或起手垅牌。为让 Godot 不重复规则判断，Bridge 需要在每一份权威状态旁提供仅用于显示的字段：

```ts
interface HandPresentation {
  lockedHandMelds: Array<{
    id: string;                 // 稳定：类型 + 排序后的 card ID
    type: 'triple' | 'quadruple';
    label: '坎' | '提';
    cardIds: string[];
    isConcealed: true;
    draggable: false;
  }>;
}
```

约束：

1. 该字段只能由 core 同一套 `MeldDetector` 计算，并随 `GameState` 一同返回；Godot 不自行把三张相同牌判定为锁定。
2. `lockedHandMelds.cardIds` 必须和 `availableActions.discard` 互斥。若发现交集，Bridge 拒绝生成该展示状态并记录协议错误。
3. 起手垅、碰、吃、招等已移到 `melds` 的牌继续使用公开组合区域，不重复出现在暗搭子区。
4. 对手的隐藏手牌绝不暴露 `lockedHandMelds` 的牌面；只允许公开 `melds` 显示。

### 拖动行为

拖动是个人布局偏好，不是游戏动作。它不提交到 Bridge，不改变 `GameState.cards` 的顺序，也不影响 AI、回放、合法动作或结算。

- 仅普通单牌可拖动。鼠标左键按住普通牌后，牌面跟随指针；拖到任意普通牌之前或之后时，松开左键吸附到该目标位置。
- 顺、二七十、对子、大小搭只作为自动理牌的视觉边界，不能整体拖动；用户要拆组时，直接拖动其中一张单牌即可。这样每次拖动都有唯一的牌 ID 和目标槽位，不会把视觉分组误当成规则动作。
- 暗搭子与已亮组合不发起拖动，悬停提示“规则锁定，不可拆散”。
- 拖动过程在原位置保留低透明占位槽；指针越过相邻牌中线时，目标牌及其后的牌以 120-160 ms 的缓动横向避让，形成可预判的插入间隙。被拖牌提升层级、轻微放大并投下短阴影；离开手牌轨道时，候选间隙清除，其余牌平滑回位。
- 松开左键后，若落在有效普通手牌轨道内，目标牌以 160-200 ms 回弹吸附到插入槽位，其余牌同步归位；若落点无效，则回弹到原始槽位。拖动不触发出牌。
- 在出牌阶段，将普通牌拖到牌桌中心的“出牌区”并松开，即等同点击“出牌”。只有当前玩家为玩家 0、`phase=discarding`，且该 card ID 仍存在于 core 返回的 `availableActions.discard` 中时，Godot 才提交同一张标准卡牌对象；提交后立即清除拖拽态，等待 Bridge 返回权威快照。
- 响应、摸牌、AI 回合、结算、弹层打开或牌 ID 已失效时，中心区不接受出牌拖放，牌面回弹原位；拖到对手区、牌山、动作按钮或中心区以外的位置也不触发动作。
- 收到新的 core 快照时，保留还存在的卡牌 ID 顺序；新摸牌放在末尾并以短暂高亮提示；已离手的 ID 删除；锁定牌移入暗搭子区。
- “理牌”按钮提供三个明确模式：`自由`（保留拖动顺序）、`自动`（普通牌按可读结构排布）、`牌序`（大小写与数值排序）。切换只重排普通牌，不移动暗搭子或公开组合。

### Godot 实现建议

- 新增 `HandLayoutState`，仅保存 `orderedFreeCardIds`、当前拖拽 ID、插入索引和每局 `replayId`；持久化到 `user://`，不写入 Bridge 状态或回放规则快照。
- 使用左键 `InputEventMouseButton` / `InputEventMouseMotion` 实现单牌拖拽，而不是系统级“拖动数据”默认预览。拖拽会创建一张仅用于视觉的浮动牌，payload 只保存 `cardId`、源索引和 `layoutRevision`；每次松开前验证 ID 仍在当前普通手牌集合中。
- 普通牌轨道按当前插入索引重新计算各牌目标位置，使用 Tween 同时处理占位间隙、相邻牌避让、无效落点回弹和有效落位。动画只改变 `Control.position`，不改变 core 快照与卡牌对象。
- 中心弃牌区提供明确的 `discardDropZone` 命中矩形与“拖到此处出牌”反馈。鼠标进入时仅在当前合法出牌阶段显示金色边框与目标卡牌占位；松开后复用现有 `_submit_discard()` 的合法性校验和 Bridge 动作守卫，不能为拖放新增旁路提交逻辑。
- 将当前 `_hand_group_column()` 拆为 `LockedMeldColumn`、`FreeHandGroup`、`DraggableHandCard` 三类组件或脚本。渲染层不再直接用 `_hand_groups()` 决定“是否不可拆”。
- 暗搭子采用现有牌面纹理的低饱和/低亮度覆盖层，而不是改造 core 卡牌数据；保留搭子类型和张数，避免训练玩家把“暗”误解为不存在的牌。

## 牌面与信息层级

- 保持纯数字牌面与毛笔字体，大小写差异继续通过现有牌面资产、红黑色和局部角标体现，不恢复“大/小 + 数字”文字。
- 普通手牌采用较大、间距稳定的牌列；暗搭子采用较窄的纵叠列，视觉上形成截图中的灰黑搭子块。
- 中心目标牌使用比手牌更清晰的数字字形；不能因毛笔字过大而影响 6/8/9 等识别。
- 已亮组合靠近所属座位，暗搭子只在本方底部手牌区显示。对手只显示背牌数量和已亮组合。
- AI 建议不在桌面上覆盖候选数字。建议触发后只高亮推荐的合法普通手牌，并保留用户确认出牌。

## 改动范围与顺序

### 阶段 A：规则展示契约

1. 在 core/Bridge 添加 `handPresentation.lockedHandMelds`，复用 core 的锁定牌检测。
2. 添加 Bridge 测试：坎/手中四张同牌出现锁定组；锁定 ID 不出现在弃牌动作中；顺、二七十、对子不进入锁定组；公开 meld 不重复出现。
3. 协议字段为可选，先保持旧 Godot 可运行；新 Godot 缺字段时降级为“全部普通牌”，绝不自行锁定。

### 阶段 B：Godot 牌桌重排

1. 将两名 AI 布局调整到左上、右上，并收紧状态条。
2. 用中心目标牌与就地响应区替换底部横向响应按钮；保留 option 预览与严格的 option ID 提交。
3. 拆分手牌区为“暗搭子 / 自由普通牌 / 已亮组合”，接入 `lockedHandMelds`。

### 阶段 C：自由拖动与本地布局

1. 实现普通单牌的左键拖放、插入槽位、相邻牌避让及自由顺序持久化。
2. 实现新快照合并策略和三种理牌模式。
3. 加入拖动占位、落点高亮、中心出牌区、锁定搭子提示和新摸牌提示。

### 阶段 D：体验验收

1. 1280x720、1024x640 与可调整窗口检查，确保手牌、中心响应和对手区不重叠。
2. 真人出牌、吃/碰/招/胡多方案、过牌、自动 AI 推进、回放重放分别验证。
3. 普通轨道内拖动前后请求 `/api/game/state`，断言状态和 `availableActions` 未变化；仅 `HandLayoutState` 改变。合法出牌阶段拖入中心区时，断言只提交 core 返回的该张 `discard` 动作，并以返回快照更新牌局。
4. 固定 seed 出现坎/垅的用例检查暗搭子不可拖、不可选、不可提交；普通顺/二七十/对子中的每张牌可独立拖动，且不支持整体拖动。

## 验收标准

- 玩家在 1280x720 首屏即可看清“谁打了什么牌、自己能做什么、哪些手牌能移动”。
- 响应阶段操作距离目标牌不超过一个中心操作区，不需要滚动或查找底栏。
- 暗色搭子完全由 core/Bridge 声明，且没有任何锁定卡牌能够通过 UI 或键盘选中并提交弃牌。
- 普通手牌拖动后视觉顺序保持稳定；切换页面、AI 走牌、重连和回放不会造成重复牌、丢牌或规则状态变化。
- 所有动作仍只由当前 `availableActions` 生成，并由 Bridge 动作守卫再次校验。

## 交互与空间修订（2026-08-14）

- 1280×720 基准下，玩家牌宽由 38 px 提升到 57 px，牌面文字随牌宽放大 1.5 倍；较矮窗口最低保持基准尺寸的 90%。
- 每张手牌渲染为约 57×62 px 的独立顶部牌面，只展示顶端文字区；同列牌之间保留至少 3 px 间距，不以后一张牌覆盖前一张牌。玩家面板不再为完整牌长占用桌面。锁定暗搭子继续和普通手牌共用同一轨道，不设置独立侧栏。
- 普通手牌拖入轨道后会显示 140 ms 插入避让；拖到其他牌列时横向吸附并按落点加入该列，拖到列间空白处时拆成新列。松手后以 version 2 二维列结构更新本局 `hand_layouts`，并兼容读取旧的一维牌序；右侧“理牌”可清除本局手动布局并恢复自动组合。
- 牌局页隐藏全局品牌导航和状态条，只在牌桌右上角保留“返回”“设置”；取消底部动作栏，中央牌桌承担响应动作和整块出牌投放。
- 手牌区只在右侧保留紧凑“理牌”按钮；移除拖动、重排、选择出牌等常驻操作提示。中央出牌命中区域在拖动时实时读取布局后的全局矩形，避免缓存旧尺寸导致动作未提交。
- 新局以 AIService 的 `game_generation` 为边界，强制清除上一局手动牌列并恢复自动组合；玩家1、玩家2席位扩大为约 464×172，公开组合牌以大字号纯文字组块显示，牌山移至中央桌面上边缘。
- 自动理牌会把未成完整组合的同值大小牌收为“大小搭”列，其余散牌各自成列，不再把所有散牌压成一列。
- 顶部品牌栏、状态栏和对手席改为紧凑布局；玩家手牌面板同步缩短，把中心桌面空间还给当前牌与响应动作。对手席统一显示为“玩家1”“玩家2”。

## 场景化牌桌布局（2026-08-14）

- `scenes/table/table_surface.tscn` 是牌桌的总布局：右上导航、两侧对手席位、中央区和底部手牌区都可在 Godot 2D 编辑器中直接选择并拖拽，锚点与边距保存在场景文件中。
- `scenes/table/opponent_seat.tscn`、`center_area.tscn`、`player_hand_area.tscn` 分别承载对手、中心出牌区和本人手牌区的固定视觉层级；脚本只把实时玩家、牌面、响应按钮和可拖动卡牌填入预留节点。
- 编辑方法：在 Godot 文件系统中双击 `table_surface.tscn`，选中 `OpponentLeftSlot`、`OpponentRightSlot`、`CenterSlot` 或 `PlayerAreaSlot` 后，使用 2D 视图的移动手柄或 Inspector 的 Layout / Anchors / Offsets 调整。编辑子区域内部间距时，打开对应子场景即可。
- `CenterSlot` 与 `PlayerAreaSlot` 在玩家响应阶段会由脚本临时腾出纵向空间；其余位置、尺寸和锚点均以场景为准。不要改动这些节点名称，它们是实时内容注入的定位点。
